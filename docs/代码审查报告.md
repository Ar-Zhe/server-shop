## 1. 已修复（本轮）

### 1.1 高危：可被玩家利用或造成资产损失

**① 摊位价格 × 数量 long 溢出 → 凭空造钱（普通玩家可用，无需 OP）**
`ShopManager.stallBuy` 用 `long total = entry.price * buyCount;`，而摊位单价完全由玩家输入且无上界
（`stallSetPriceNew`/`stallApplyPrice` 只截负数）。甲用小号上架 3 个圆石、单价设 2^62，乙（另一账号）
买 3 个 → `total` 溢出为 **负数** → `buyer.balance < total` 恒不成立 → `balance -= 负数` 让小号
**凭空 +4.6e18**，随后可清空每日商店、压过任何拍卖。数量填 4 时 `total = 0`，还能 0 元拿货。
> 修复：新增 `parsePrice()`（价格上界 = `maxBalance`，谁也付不起的价格直接判非法）+ `safeMultiply()`
> 溢出保护；`buyShop`（每日商店）、`sellBuyback`、`stallBuy`、拍卖起拍、管理员配置价格全部改用它。

**② 邮件"部分领取"不落盘 → 定时重启后复制物品**
`claimMail`/`claimAllMail` 在背包放不下时把 `entry.stack` 改成余量，却**没有 `setDirty()`**。
已核对 vanilla：`SavedData.save(...)` 第一行就是 `if (this.isDirty())`，`DimensionDataStorage.save()`
也只是遍历调用它 —— 没标脏 = 不写盘。于是「塞满背包 → 部分领取 → 定时重启/崩溃」后邮件恢复原数量，
玩家白拿一份。`/save-all` 也救不回来（同样只写 dirty 数据）。
> 修复：两个部分领取分支补 `setDirty()`。

**③ 掉线/停服时退还的物品写进"已落盘"的背包，实际丢失**
`DepositMenu.removed()` 与 `GrantMenu.removed()` 在关闭界面时把槽内物品 `add` 回背包。
vanilla 事件顺序（`PlayerList.remove`：`firePlayerLoggedOut` → **`this.save(player)` 落盘** →
`removePlayerImmediately` → `Player.doCloseContainer` → `removed()`）意味着**退还发生在写盘之后**，
之后不再保存该玩家 → 物品消失。vanilla 自己的 `AbstractContainerMenu.clearContainer` 正是
「`hasDisconnected()` 时直接 `player.drop(...)`」。
> 修复：两个菜单在 `player.hasDisconnected()` 时改为掉落（掉落实体随世界保存，不会丢）。

**④ 交易被永久卡死（接受请求即触发）**
`TradeManager.acceptRequest` 先 `BY_PLAYER.put(playerB, 本会话)`，紧接着循环取消该玩家的其它待同意请求，
而 `cancelInternal` 里是 `BY_PLAYER.remove(other.playerB)` **无差别删除** —— 把刚写好的映射又删掉了。
此后接受方 `sessionOf()==null`，点「同意/确定交换」全部静默无效；同时 `busy()` 恢复 false，
可在旧会话仍持有物品时开第二笔交易（单一会话不变式被打破）。
> 修复：先清理其它请求、再写 `BY_PLAYER`；`cancelInternal` 改用 `Map.remove(key, value)` 只删仍指向本会话的映射。

**⑤ 管理员发放金额溢出 → 全服余额被写成巨负（我新增功能的 bug）**
`Math.min(max, before + amount)` 在 `amount` 极大时先溢出成负数再被 min 取负。
`/shop admin money 9223372036854775807` 会把所有余额 > 0 的玩家写成约 −9.2e18。
> 修复：新增 `credit()` 饱和入账（先算剩余空间再取小，永不溢出）；命令入口再加 `rejectHugeAmount()`
> 直接拒绝超过 `maxBalance` 的金额（实测已生效，见第 4 节）。

**⑥ 输入弹窗在窗口 resize 后发送旧值（客户端）**
`ShopInputScreen.init()` 每次调用都往 `boxes` 列表追加，从不清理；而 `Screen` 在 resize 时会重新
`init()`。于是 `boxes` 变成 2N 条，`setInitialFocus(boxes.get(0))` 聚焦到已不在界面上的旧输入框，
`confirm()` 读的也是旧值 —— 玩家把数量从 1 改成 20、拉一下窗口再确认，服务端收到的是 **1**。
> 修复：`init()` 开头记录并清空 `boxes`，重建后优先恢复玩家已输入的内容。

### 1.2 中危：资产销毁 / 数据完整性

**⑦ 管理员幽灵槽模板被当真实物品返还 → 刷物品**
`ShopManager` 的注释明确写着「模板绝不作为真实物品返还」，但：
- `adminSetPriceNew` 在价格非数字时 `addItemOrMail(player, stack, SOURCE_ADMIN)`（stack 是幽灵槽模板副本，
  原物已在管理员背包里）→ 输入一个非数字价格就白得一件；
- `adminRemove` 下架时 `addMail(..., removed.stack.copy(), ...)` 把池中模板邮寄回来 → 同样白得一件。
> 修复：这两处不再返还模板（只提示/只移除）。

**⑧ 邮件过期会把未领取的资产一起删掉**
`tickDaily` 的 `removeIf(mail -> day - mail.receivedDay >= expireDays)` 没有判断 `pending()`，
未领取的物品邮件、未查看的货款邮件会被直接删除；旧存档缺 `receivedDay` 时读出 0，`day - 0` 必然超期。
（默认 `mailExpireDays=0` 不触发，一旦服主开启就会清空历史邮件。）
> 修复：只清理 `!pending()` 且 `receivedDay > 0` 的邮件。

**⑨ 塞满背包时"买了却买不到"（每日商店）**
`buyShop` 用 `player.getInventory().getFreeSlot() < 0` 预判背包已满 —— 没有**空槽**但同类还能堆叠时
会误报「背包已满」直接拒绝购买，而下面的邮箱兜底永远走不到；与摊位购买行为不一致。
另外 `reward.setCount(buyCount)` 可能超过单栈上限（例如 5 个鞘翅一叠），生成非法物品栈。
> 修复：去掉预检，统一走新的 `deliver()`（按 `maxStackSize` 拆份 → 先背包、后邮箱）。

**⑩ 收购时金币被余额上限吞掉**
`sellBuyback` 先把物品收走再 `Math.min(maxBalance, balance + total)`：余额接近上限的玩家卖东西会
**货没了、钱也没了**。
> 修复：先算剩余额度，额度不足直接拒绝/夹取数量，物品不再被白收。

**⑪ 管理员发放的三个稳健性问题（我新增功能）**
- 客户端用 `all` 标记 → 服务端按"当前全表"展开，会把管理员界面上从未看到的、期间刚登录的玩家也一起发放；
  → 修复：客户端**始终发送显式 UUID 列表**。
- 单个目标投递异常会中断整批（物品已离手、后续目标拿不到）→ 修复：逐目标 try/catch + 失败计数回报。
- 目标邮箱已满时物品会改走背包/掉落，管理员却只看到"发放完成"→ 修复：回报"N 名玩家邮箱已满"，
  并在"每人邮件数 > 邮箱上限"时提前提醒分批发放。
- `sendTargets` 自身无权限校验（当前调用点都有校验，属防御纵深）→ 修复：方法内自查。

**⑫ 其它低危修正**
- `stallBuy` 买家邮件用了 `SOURCE_STALL_UNSOLD`，邮箱里会显示成「你上架的物品没卖出去，已退还」
  → 新增 `SOURCE_STALL_BOUGHT` + 文案。
- `doTransfer` 只刷新付款方快照，收款方界面余额还是旧值 → 补发收款方静默快照。
- `NotificationManager`：未读从 0 变正 / 被清空时没有复位提醒节流时间戳，导致"清完红点后隔几小时来一封
  邮件会立刻弹提醒" → 两处补复位。
- 管理员发放邮件在邮箱里不显示数量（64 个钻石和 1 个钻石描述一样）→ 补 `×数量`。
- 客户端「全体玩家」按钮无视搜索过滤（搜了 Steve 却选中全服）、刷新后不清理失效选择、
  计数用全表长度 → 三处一起修。

## 3. 建议优化（不改也不影响正确性）

1. **快照开销**：`sendSnapshot` 每次都会序列化「全部邮件（每封一个完整 ItemStack）+ 拍卖 + 摊位 + 在线玩家」，并且**无条件把 `adminShop`/`adminBuyback` 两个商品池发给所有玩家（含非管理员）**；`stallBuy` 一次购买还连发 3 个包（`sendSnapshot` + `broadcastSnapshots` + `openStallBrowse`），其中 `broadcastSnapshots` 对**每个在线玩家**重算全量。建议：非管理员不下发商品池、摊位变动只推给相关玩家、按 tab 裁剪字段。
2. `refreshDailyPrices` 每次都做「每日条目 × 商品池」线性匹配；可在池变更/`/shop reload` 时建 `Map<Item, ConfiguredOffer>` 缓存。
3. `tickDaily` 每 20 tick 调用 `LocalDate.now()`（有分配），可缓存当天值（`tickAuctions` 已 early-return，没问题）。
4. 客户端每帧重建全部点击区域并为每行 `new CompoundTag()`；`drawMail` 每帧 `DateTimeFormatter.ofPattern(...)`；`formatDuration` 每帧 `String.format`。都可提到 `static final` 或缓存。
5. 读类动作（`request_data`、`trade_requests_open`）无冷却，几十字节的包能换来一份全量快照，建议加每玩家最小间隔。
6. `Rarity.byId`/`MailType.byId` 对未知 id 静默降级为 COMMON/ITEM（`ShopNbt.loadStack` 解析失败也静默变空气且无日志）：模组物品被移除、或未来改名时会**静默吞掉商品/拍卖标的/邮件物品**。建议至少 `LOGGER.warn` + 保留原始 NBT 便于人工恢复；`Rarity` 已有 `byIdOrNull` 可直接用。
7. `ShopSavedData.load` 每次都会 `seedDefaultsIfEmpty()`：管理员把商店池和收购池**同时清空**后，重启会被默认商品池还原（含 8000 的 NETHER_STAR）。建议只在首次创建时播种。
8. `nextAuctionId`/`listingCounter` 在旧存档缺字段时重置为 1，而既有拍卖/摊位订单号不变 → 可能出现重复 id（`placeBid` 取第一个匹配项 → 出价打到别人的拍卖单）。建议取 `max(已有 id)+1`。
9. `dailyShop.bought`/`limit`、`stall.stock` 读档时不夹取，负值会让限购被放大 / 退还逻辑被跳过。
10. `Config.antiSnipe` 默认 true 但 `antiSnipeExtensionSeconds` 默认 0，延长条件要求 `>0` → 默认配置下防狙击等于没开。

## 5. 附：审查证据与复核方法

- 关键结论均以「反编译源码 + 实际行为」双向确认：
  - `SavedData.save(File, Provider)` 首行 `if (this.isDirty())` → 缺 `setDirty` 即不落盘（github 项 ②）。
  - `PlayerList.remove` 中 `this.save(player)` 在 `removePlayerImmediately → doCloseContainer` **之前**
    → 掉线退还写背包必丢（项 ③，vanilla `clearContainer` 用 `hasDisconnected()` 分支掉落，是官方范式）。
  - `ItemStack.copy()` → `components.copy()` → `new PatchedDataComponentMap(prototype, patch, true)`：
    patch map 是写时复制，但**组件值对象仍共享**。原版组件不可变所以安全；模组里"把可变容器当组件值"的物品
    （本服装有精妙背包/精妙核心）存在内容物串号风险。作者自己写了 `ShopNbt.deepCopy` 并只在交易里用了，
    商店/摊位/邮箱交付路径仍是 `.copy()` —— 建议统一，实测方法：把装有物品的潜行盒经幽灵槽加入商品池，
    A 购买后修改内容物，B 再买同一条目，看内容物是否串号。
  - `PayloadRegistrar.thread` 初始值 = `HandlerThread.MAIN` → 服务端动作包在主线程执行（排除并发误报）。
